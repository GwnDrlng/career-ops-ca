Deep-Dive — The Opus Budget Guardrail

One guardrail, end to end — a worked example of how the whole safety layer is designed.

The problem

The ≥3.7 lane spends real money on Opus 4.8: judge → grounding-check, and a failing judge triggers up to two revise-and-re-judge retries. One application can fan out to 4–6 Opus calls, so a routing bug or retry loop could quietly burn a month's budget in an afternoon. Cost is invisible until the bill arrives, so it needs a hard automatic stop — not a dashboard you remember to check.

The core invariant: one chokepoint, gate-before / record-after

Every Opus call goes through a single function — opus-call.mjs → callOpus(). Nothing calls claude -p directly. That chokepoint checks the budget before the spend and records actual cost after it, so the ledger is always the source of truth and any new caller inherits every ceiling for free.

sequenceDiagram
    autonumber
    participant Lane as judge / grounding / applier
    participant Opus as opus-call.mjs
    participant Budget as token-budget.mjs
    participant Ledger as token-usage.tsv
    participant Audit as audit-log.tsv
    Lane->>Opus: callOpus(prompt, lane, {jobId})
    Opus->>Budget: gate --job-id ID (BEFORE spend)
    Budget->>Ledger: sum 4 windows
    alt any ceiling breached
        Budget->>Audit: budget.halt (job-scoped)
        Budget-->>Opus: exit 1
        Opus-->>Lane: ok:false, haltedByBudget — no tokens spent
    else under all ceilings
        Budget-->>Opus: exit 0
        Opus->>Opus: claude -p (the spend)
        Opus->>Budget: record --cost-usd C --job-id ID (AFTER)
        Budget->>Ledger: append row
        Opus-->>Lane: ok:true + cost
    end

Four ceilings, three shapes — matched to what each protects

5-hour token block
rolling 5h · trips at 75%
Rolling window matches Anthropic's usage block — it's what actually refills.
Weekly token allowance
rolling 7d · trips at 60%
Same reasoning, weekly grain.
Monthly cost cap
calendar month · trips at 75%
Anchored to the 1st (billing-aligned). A % ceiling leaves headroom to finish in-flight work by hand.
Per-application cost cap
all-time, one job_id · hard 100%
A per-item budget, not a buffer on a shared pool — so a hard line, scoped by a grouping key in the ledger.

The percentage-vs-hard-cap split is the key call: a shared pool (monthly) wants a margin so you're warned before you're broke; a per-item budget (per-application) wants an exact line — "never spend more than $X on one application" means $X, not 75% of it.

Why per-application needed a schema change
Monthly is a global rollup — no notion of which job. Per-application is sum WHERE job_id = X, and that key didn't exist. So it added a job_id column + threaded an id through 4 files; the monthly cap needed none. Splitting the two kept each change reviewable.
Honest limitation: cost is known only AFTER the call
claude -p reports cost on return, so the gate blocks the next call, not the first over-budget one. Monthly tolerates one call of overshoot; per-application is tighter, so a future pre-call estimate could block proactively. Logged as accepted risk, not ignored.
Fail-closed vs fail-open, per component
Budget gate + kill switch fail closed (unclear state → halt/pause — never spend/act on doubt). The audit log fails open (a write error never breaks the observed action). "Fail safe" means opposite things for a spend gate vs an observer.
Config-not-code, everything auditable
Every threshold is in config/guardrails.yml — a cap change is a diff-reviewable config edit, not a script. Every halt writes a job-scoped budget.halt row, so "why did nothing draft for job 231?" is one audit.mjs tail away.
A stop, not a dead end — override or defer
On halt, Slack names the ceiling + a token and a verified approver picks: budget-override <token> to continue now (a bounded few more calls, default 3, for that job) — or budget-defer <token> to pause the whole pipeline until the next daily cron and auto-resume. Same trust model as the submit gate — approver-bound, scoped, expiring, fully audited. Override = capped, logged overspend; defer = "the budget's spent, try tomorrow." A real three-way choice, not override-or-nothing.
